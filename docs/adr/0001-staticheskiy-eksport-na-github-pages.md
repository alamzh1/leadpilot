## Контекст

Бриф требует Next.js App Router и публикацию на Vercel «или другом хостинге»; пользователь выбрал GitHub Pages (`alamzh1/leadpilot`), который отдаёт только статику и обслуживает сайт из подпути.

## Решение

Собираем сайт с `output: "export"`. `basePath` и `assetPrefix` берутся из `NEXT_PUBLIC_BASE_PATH` (пусто локально, `/leadpilot` в CI), `images.unoptimized: true`, адаптивные изображения — ручной `srcset` из двух WebP-ширин. Все пути к статике строятся только через `asset()` из `lib/site.ts`. Деплой — workflow GitHub Actions.

## Почему

- Vercel с серверным рендерингом и штатной оптимизацией `next/image` отвергнут: пользователь выбрал GitHub Pages, а там нет сервера. Сайт и так не нуждается в сервере: нет БД, авторизации, оплаты и сетевых запросов.
- Обычный `next/image` с оптимизатором отвергнут: оптимизатор в статическом экспорте недоступен, поэтому `unoptimized` и `srcset` вручную.
- Публикация без `basePath` отвергнута: на GitHub Pages сайт живёт по `/leadpilot`, абсолютные пути `/images/...` вернут 404.

## Последствия

- Любой путь к статике, написанный в обход `asset()`, работает локально и ломается на Pages. Это правило проекта, и его нельзя проверить типами, только e2e на опубликованной версии.
- Серверных возможностей (API-маршруты, middleware, ISR) нет. Если продукт обзаведётся живым анализом, архитектуру придётся менять.
- Размеры изображений выбираем и конвертируем сами; оптимизатор этого не сделает.
- Смена хостинга или адреса репозитория означает смену `basePath`.
